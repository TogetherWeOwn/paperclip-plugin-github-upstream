# Changelog

## Unreleased

- Review-guard (TWO-5794): a new `review-guard-scan` job plus `issue.created` / `issue.updated` event subscriptions stamp the configured default review stages (Security then QA by default, per-project override supported) onto any code card (bound to a project workspace) that reaches `in_review` — or is created as code work — without a live reviewer stage, with an audit comment each time. Cards with stages or `auto` mode are never touched; the guard is off by default and inert until reviewer agent IDs are configured, and `reviewGuardDryRun` logs intentions without writing. New capabilities: `events.subscribe`, `issue.comments.create`.
- Review-guard risk tiers (TWO-5879): staffing now varies by the card's changed paths (read-only `git` in the workspace checkout, matched against the repo's `.github/review-tiers.yml` `low`/`ordinary`/`sensitive` globs). QA runs on every tier; Security is added (Security → QA) only for Sensitive/unknown, and the tier is recomputed on every head — a QA-only card is upgraded (Security prepended, existing stage IDs preserved) with an audit comment when a newer head tiers Sensitive, and never downgraded. Anything unclassifiable fails closed to Sensitive (missing/malformed tier map, unreadable diff, unmapped path, editing the tier map itself). Reviewer roles became explicit via `reviewQaAgentIds` / `reviewSecurityAgentIds` plus per-project overrides (`reviewQaAgentIdsByProjectId` / `reviewSecurityAgentIdsByProjectId`); when unset, `defaultReviewAgentIds` splits by position so existing installs keep Sensitive staffing. A Sensitive head with no usable Security reviewer fails closed (no stamp) instead of downgrading to QA-only. New capabilities: `project.workspaces.read`, `execution.workspaces.read`. This repo ships its own `.github/review-tiers.yml`.

- Track follow-through owners one program level below the tracker, sharing the same owner set with audit and discovery to avoid duplicates. Explicit item origins stay authoritative when ordinary subtasks exist; only identity-bearing children identify a program without an item origin. Gate titles use a delimiter-aware match in both ownership and audit, so “gateway” items remain owners and cannot count as gate approvals. Nested owners' gates remain valid audit evidence.
- Rebind cached item ownership and initialize the new owner's origin/header/labels even on an unchanged upstream response, without an ownership-only wake. Dry runs leave the live ownership repair unconsumed.
- Clarify the mapping contract: an unquoted GitHub URL in the description (or an existing plugin origin) identifies an item. Remove the work-product-only fallback, which could not work with the host's raw subtree issue rows. Add a description link to work-product-only cards before relying on plugin tracking.

- Upstream-gate audit: new hourly `audit-scan` job. It searches recent upstream issues, PRs, discussions, comments and reviews by our account (`auditLogins` plus operator/bot identities, across `auditOrgs` and `auditRepos`) and flags any post with no approved `Upstream gate …` card (`done`, under the item's follow-through card, approved no later than the post). An ungated post labels the follow-through card `upstream:ungated` (creating it when missing) and opens one `Ungated upstream post: <owner>/<repo>#<n>` card for the Chief of Staff, woken with idempotency key `ungated:<post-url>`; per-item cursors plus recorded flag keys dedupe reruns. Posts before 2026-11-02T00:00Z are out of scope (covered by TWO-810…TWO-818). Known gap: the SDK exposes no execution-decision reads, so v1 checks `done` plus the parent link instead of verifying both review stages.
- GitHub App authentication: `appId`, `installationId` and `appPrivateKeySecretRef` replace the long-lived personal token. Short RS256 JWTs mint 1-hour installation tokens (in-memory only, refreshed 5 minutes before expiry, never logged or persisted). `tokenSecretRef` stays as the alternative; exactly one auth mode must be set.
- TWO-797 hardening: per-tick create/wake spend caps with next-tick deferral, one open intake card per repo (newer tags retitle and wake at most once), install baselines that never card the running version, closed/merged items skipped, case-insensitive owner/repo and login handling, untrusted-upstream-data sanitizing for card text, fail-closed scans (no anonymous reads), precise 403 rate-limit classification, and redirect refusal on every GitHub request.
- GitHub tab: native `IssuesList` page slot scoped by `originKindPrefix` with a stable `viewStateKey`, plus a `MetricCard` row (open PRs, red CI, awaiting maintainer, awaiting us) fed by a new worker-registered `github-upstream-summary` data key.
- Awaiting facet: `decideAwaiting` derives whose court the ball is in (us vs maintainer) from the item snapshot; `gh:awaiting/us` and `gh:awaiting/maintainer` labels sync onto tracking cards and flip on review-state changes.
- Stale `gh:*` label IDs are now swept by reverse lookup, so ID-only read paths cannot accumulate replaced facets.
- Upgrade from 0.1.0 no longer wakes every tracked card: the first scan backfills the new review-state field with one unconditioned reviews read per tracked PR and renormalizes the stored fingerprint, syncing the new awaiting labels silently.
- `decideAwaiting` returns null for non-ours open items whatever their review or CI state, matching the documented "non-ours items never get an awaiting label" contract.
- Tab metrics skip card-less records and prune records for items that are no longer tracked, so the counts agree with the visible list.
- Awaiting flips from config or label-map drift (no upstream change) sync labels/header quietly without waking.
- Manifest declares `ui.page.register` for the GitHub page slot (the host install rejected 2ab13e1 without it); a new test mirrors the host's manifest/capability consistency check so CI catches this class of error. Manifest wording now says release-intake cards are created for new tags after the install baseline.

## 0.1.0

- First release. ETag-conditional release scan (latest-release poll, one intake card per tag) and item scan (issue/PR/discussion tracking with deterministic wakes, label and description-header sync).
- Card mapping by `originId`, GitHub URL work product, and GitHub URL in the description, with `originKind`/`originId` backfill.
- Dry-run binary (`paperclip-github-upstream-dryrun`) that logs intended creates/wakes without making them.
